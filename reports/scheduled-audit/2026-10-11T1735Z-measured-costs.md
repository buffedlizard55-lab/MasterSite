## Budget arithmetic the runner now uses

The documented ceiling for the built-in Actions `GITHUB_TOKEN` is **1,000 requests/hour/repository**
(<https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api>), so the runner
holds `--budget 900` and `--reserve 60`, i.e. **840 spendable requests per run**.

| Weekday slot | Planned audits | Planned cost | Fits 840? |
|---|---|---:|---|
| Monday, Thursday | `audit_kind` + `audit_descriptions` | 435 | yes |
| Tuesday, Friday | `verify_live` | 812 | yes (28 requests of headroom) |
| Wednesday, Saturday | `audit_provenance` | 1,000 planned (904 measured) | **no** — reported `NOT-RUN`, never truncated silently |
| Sunday | full-suite attempt | 2,247 | plans `audit_kind` + `audit_descriptions` (435), then reports `verify_live` and `audit_provenance` `NOT-RUN` with the remaining budget printed |

A `NOT-RUN` audit is **not** a checked audit, and a run that covers only part of the suite reports
`PARTIAL`, never a pass. Closing `audit_provenance` in one run needs either an owner-provided
fine-grained token (5,000 requests/hour, T-023), a deliberate shard of that audit, or a dispatch with
an explicit `--reserve 0`.

## Method

1. Scratch clone: `git clone /home/user/MasterSite /tmp/measure2/repo` (the checkout has no
   `tools/.readme-cache`, which is git-ignored — so this was a **cold-start** measurement; 239 cache
   files were written *during* the run, none copied in).
2. [`raw/counting_shim/sitecustomize.py`](raw/counting_shim/sitecustomize.py) was placed on
   `PYTHONPATH`. It wraps `urllib.request.urlopen` and writes every requested URL to
   `count-<tool>.json` at process exit — it changes no tool behaviour and no request is added or
   removed.
3. [`raw/measure_costs.py`](raw/measure_costs.py) ran the four audits in the runner's own order
   (`audit_kind`, `audit_descriptions`, `verify_live`, `audit_provenance`), timing each and recording
   its exit code, with `GITHUB_TOKEN` set.
4. Raw evidence: [`raw/measure_costs.json`](raw/measure_costs.json) (summary) and
   [`raw/count-audit_kind.json`](raw/count-audit_kind.json),
   [`raw/count-audit_descriptions.json`](raw/count-audit_descriptions.json),
   [`raw/count-verify_live.json`](raw/count-verify_live.json),
   [`raw/count-audit_provenance.json`](raw/count-audit_provenance.json) (one URL per request, query
   strings stripped). The tools' own output is not committed; the audits' verdict files in
   `tools/last_*.json` are the published result of the runs.

A `GET /rate_limit` delta was tried first and **abandoned**: from that environment the endpoint
reported `remaining 5000 / used 0` even after confirmed HTTP 200 responses, which matches GitHub's
own note that these counters vary by region and that the `x-ratelimit-*` headers are authoritative.
Counting requests client-side, as above, does not depend on that endpoint.

## Caveats

- Point-in-time counts (2026-10-11, 145 listed entries, 146 public repositories). `verify_live`
  paginates every repository's commit list, so its cost grows with commit history; `audit_kind` and
  `audit_descriptions` grow linearly with the census; `audit_provenance` grows with the number of
  cited endpoints. Re-measure after a census refresh instead of assuming these numbers.
- The tools share `tools/.readme-cache` inside one run, so an identical README read by a later tool is
  served from disk without a request. The counts above include that saving (this is also why a
  narrower run can cost proportionally *more* than the same tool does here).
- The measurement token was a sandbox token with a 5,000 requests/hour limit; the schedule runs on the
  built-in Actions `GITHUB_TOKEN` at 1,000 requests/hour/repository. This file is about **cost**, not
  about which token pays it.
- Request counts are not verification results. A cheap audit that finds nothing is still evidence; an
  expensive one that was cut short is not.
